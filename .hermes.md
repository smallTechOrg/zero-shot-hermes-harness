# Zero-Shot SDD Skills (v2) — Hermes skill harness

This repo is a **skill package**: three spec-driven-development skills
(`zero-shot-build`, `zero-shot-fix`, `zero-shot-sync`) plus the shared roles,
patterns, and rules they reference. It is repo-independent — install it into
Hermes and the skills operate on *whatever project repo you point them at*, not on
this repo. There is no default stack and no boilerplate: the spec derives the stack
from the requirements, and every spec includes `spec/agent.md` — the AI-native design
lens, which may legitimately conclude "no AI capability needed".

## Install

```bash
hermes skills tap add smallTechOrg/zero-shot-harness
# then in a Hermes session:
/reload-skills          # or restart Hermes
```

This taps the repo's top-level `skills/` directory. Hermes reads the skills
from here; any skills Hermes creates or learns on its own go to
`~/.hermes/skills/` — separate location, no collision, no overwrite.

(Per-skill `hermes skills install` also works; it copies only each skill directory, so
you must additionally place the repo's `support/` tree at `~/.hermes/support` — the
README shows the exact commands. Without it the skills' `../../support/…` references
don't resolve.)

## Layout

```
skills/
  zero-shot-build/   SKILL.md + references/
  zero-shot-fix/     SKILL.md
  zero-shot-sync/    SKILL.md
support/             shared material the skills reference (via ../../support/…)
  agents/            spec-writer, code-generator, qa-auditor (dual-mode role files)
                     + project-builder (Claude-only — NEVER run or delegate on Hermes)
  patterns/          spec-driven, phases, agentic-ai, test-driven, ui-ux, …
  rules/             ai-agents, git, secret-hygiene

.claude-plugin/, agents/, CLAUDE.md    Claude Code wrapper — not used by Hermes
```

## Invoking

The skills are `disable-model-invocation: true` — trigger them explicitly:

```
/zero-shot-build <idea>
/zero-shot-fix <bug | error | "tests" | "drift">
/zero-shot-sync [scope]
```

Routing (for plain-English use): build = new project / add capability; fix =
broken behaviour / failing test / error; sync = reconcile spec ↔ code (spec
wins). The `SKILL.md` IS the process — follow it exactly, never improvise.

## Hard rules (survive context compression)

- README must always be accurate — every command works exactly as written.
- Never claim a test passed if you didn't run it. Show output.
- Real-service testing only. A stubbed pass is not a pass; a present-but-dead key
  (401) is a BLOCKER naming the env var.
- Launch the app with the project's pinned runtime via its documented entry command
  (Python example: `.venv/bin/python -m src` — never bare `python`). Only the root
  session serves; verify the URL live before presenting it.
- When the project calls an LLM: one batched call per artifact — never a call per
  output line/token.
- Git hygiene when the skill drives a build in *another* repo: commit+push as
  one atomic action, stage specific files (never `git add -A`), never stage
  secrets; the build's PR targets the branch it was cut from, and the user merges it.
